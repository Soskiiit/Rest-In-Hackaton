# ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ): ОФФЛАЙН 3D-МЕТАВЕРС (THREE.JS + LAN + AI)
> **Контекст:** Разработка на хакатон (мотив: *«Ready Player One / Первому игроку приготовиться»*).  
> **Сформировано на основе:** Официального задания (`task.txt`) и расшифровки открытия/требований организаторов и жюри (`output.txt`).

---

## 1. Концепция и социальная значимость проекта

### 1.1. Главная идея
Разработка интерактивного многопользовательского 3D-пространства в браузере (Three.js), работающего **строго локально по LAN/Wi-Fi без доступа в интернет**. Игроки исследуют мир, взаимодействуют друг с другом и с адаптивными ИИ-агентами (NPC).

### 1.2. Социальная и образовательная польза (Требование жюри)
Жюри **категорически запретило** делать бессмысленные экшены/GTA/«Breaking Bad». Проект обязан нести понятную пользу.  
Рекомендуемые темы:
1. **Интерактивное изучение языков:** Общение с NPC-носителями, диалоги, задания на понимание контекста, визуализация предметов на изучаемом языке.
2. **Историко-культурные эпохи:** Погружение в конкретные эпохи, диалоги с историческими деятелями (Геродот, Эйнштейн, Архимед, Ломоносов), разбор исторических событий.
3. **Виртуальные лаборатории и наука:** Опыты по физике/химии, наглядная математика, моделирование законов природы.
4. **Медицина катастроф / Безопасность / Первая помощь:** Отработка алгоритмов спасения, сортировки пострадавших, реакция на ЧС.
5. **Практические жизненные навыки / Профориентация:** Симуляция реальных процессов (навигация, оформление документов, решение ситуационных кейсов).

> **Фокус:** Качественная проработка сценария + польза + красивая визуализация = максимальный балл по концепции.

## 3. Архитектурные и технические требования

### 3.1. Клиентская часть (3D-движок & UI)
- **Технологии:** Three.js (WebGL / WebGPU). Разрешено использование библиотек/WASM, если команда может объяснить профит в производительности.
- **Интерфейс:**
  - Окно 3D-вида от первого или третьего лица с плавным управлением (WASD + мышь).
  - UI авторизации/регистрации (вход в сессию).
  - Текстовый/интерактивный чат для общения игроков между собой.
  - Диалоговый интерфейс взаимодействия с NPC (история сообщений, поле ввода, подсказки/действия).
  - Индикатор производительности / дебаг-панель (FPS, % загруженного мира, координаты игрока, статус сети).
- **Производительность:**
  - Стабильные 60 FPS на средних ноутбуках.
  - Оптимизация геометрии, инстансинг (`InstancedMesh`), сжатие текстур/ассетов.
  - Корректная утилизация и очистка памяти (освобождение `geometry.dispose()`, `material.dispose()`, удаление объектов из сцены).

---

### 3.2. Ключевое ограничение: «Не более 10% мира на клиенте»
> ⚠️ **КРИТИЧЕСКОЕ ТРЕБОВАНИЕ ЖЮРИ:** Клиент не имеет права загружать весь мир сразу. В памяти браузера разрешено держать **не более 10%** от всех данных виртуального мира.

#### Механизм реализации (Spatial Streaming / Chunks / AOI):
1. **Сетка чанков (Grid / Chunks):**
   - Весь мир разбит на виртуальные сектора/комнаты/чанки (например, 10x10 = 100 чанков).
   - Сервер хранит мастер-карту мира и все объекты (метаданные, геометрию, текстуры/параметры, NPC).
2. **Динамическая подгрузка по положению (Area of Interest):**
   - Клиент отправляет свои координаты $(x, y, z)$.
   - Сервер отдает только текущий чанк и соседние (радиус видимости, максимум 4–9 чанков из 100, что строго $< 10\%$).
3. **Строгая выгрузка (Unload / Garbage Collection):**
   - При переходе игрока в другую зону чанки за пределами радиуса видимости удаляются из Three.js сцены и оперативной памяти (`dispose`).
4. **Валидация для жюри:**
   - Вывести на экран счетчик: `Кешировано данных: X% (Лимит: 10%)`.
   - Возможность показать жюри в консоли/Network/Memory Profiler, что удаленные объекты реально выгружаются.

---

### 3.3. Сетевой уровень и многопользовательский режим (Multiplayer)
- **Окружение:** Полный оффлайн! Ноутбуки объединены в локальную сеть через Wi-Fi роутер или мобильную точку доступа (2–4+ клиентов одновременно).
- **Протокол:** Двунаправленный обмен данными через **WebSocket** (или WebTransport/WebRTC DataChannels). Поллинг (HTTP polling) запрещен/крайне не рекомендуется организаторами.
- **Авторизация:**
  - Сетевой обмен игровыми событиями доступен **только после авторизации**.
  - Идентификация игрока (токен сессии, логин/никнейм).
  - Желательно шифрование трафика (WSS / TLS с самоподписанным сертификатом или симметричное шифрование сообщений/токенов).
- **Синхронизация:**
  - Позиции, вращение и анимации других игроков.
  - Интерполяция движения (lerp), чтобы персонажи двигались плавно без рывков по тикам.
  - Spatial Audio / видимость: сервер уведомляет клиентов о событиях в их зоне (приближение к помещению/комнате с другими игроками).

---

### 3.4. Персистентность и База Данных (Server State)
- **Хранилище:** Серверная БД (SQLite / PostgreSQL / embedded DB / JSON-хранилище на сервере).
- **Сохраняемые сущности:**
  - Профиль игрока (логин, пароль/хэш, инвентарь/прогресс, очки, аватар).
  - Последние координаты игрока в мире (при реконнекте игрок появляется там, где остановился).
  - Состояние взаимодействия с NPC (история фактов, которые игрок уже узнал, пройденные этапы квестов).
- **Критерий жюри:** При перезапуске клиента или остановке/перезапуске сервера состояние мира и игроков восстанавливается.

---

### 3.5. Автономные ИИ-агенты (NPC)
> ⚠️ **КРИТИЧЕСКОЕ ТРЕБОВАНИЕ:** ИИ-вычисления должны проводиться **исключительно локально**, без доступа к внешним облакам (OpenAI, Anthropic и т.д.).

#### Архитектура ИИ:
1. **Характер и индивидуальность:**
   - У каждого агента есть свой контекст/профиль/роль (например: *Эйнштейн* — теория относительности, мысленные эксперименты, немецкий акцент/тон; *Геродот* — путешествия, Древний Египет, античные мифы).
2. **Адаптивность (Memory & Dynamic Context):**
   - **Не захардкоженные скрипты!**
   - Агент помнит, о чем уже говорил с данным игроком.
   - Если вопрос задается повторно — агент не повторяет текст слово в слово, а дополняет или мягко напоминает: *«Как я уже упоминал ранее...»*.
   - Тон и глубина ответа адаптируются к прогрессу игрока.
3. **Техническая реализация (на выбор/комбинация):**
   - **Локальная LLM:** Ollama / llama.cpp / Transformers.js / ONNX Runtime Web / Small quantized model (Llama-3.2-1B/3B, Qwen-2.5-1.5B/3B, SmolLM2, Phi-3.5).
   - **Гибридный подход (надежно для хакатона):** Локальная LLM + Конечный автомат (FSM) + Векторная память / Семантический поиск (RAG по локальной базе знаний) + Коллаборативная фильтрация тем.
   - Система состояний: IDLE -> NOTICE_PLAYER -> GREETING -> DIALOGUE -> TOPIC_COMPLETED.

## 5. Вопросы жюри на защите: Чему уделить внимание

Жюри будет не просто смотреть демо, но и тестировать на прочность архитектуру. Команда должна уверенно отвечать на вопросы:
1. *«Покажите, как соблюдается правило 10% данных мира?»*  
   → Демонстрация вкладки Network/Memory в DevTools: показать, что подгружаются только соседние чанки, а старые геометрии очищаются через `dispose()`.
2. *«Что произойдет, если отключить интернет-кабель/роутер от глобальной сети?»*  
   → Показать, что проект крутится исключительно на локальном хосте/LAN, внешних CDN нет, все скрипты, шрифты и модели лежат локально.
3. *«Где и как сохраняется состояние игрока?»*  
   → Показать серверные логи, таблицу в БД, сделать перезагрузку страницы — игрок восстанавливается с сохранением прогресса диалогов с NPC.
4. *«В чем заключается адаптивность NPC?»*  
   → Продемонстрировать 2 последовательных диалога с одним NPC: показать, как меняется ответ в зависимости от истории.
5. *«Почему вы выбрали именно эти библиотеки/движок?»*  
   → Четкое обоснование выбора (скорость разработки, GPU-рендеринг, легковесность протокола).
